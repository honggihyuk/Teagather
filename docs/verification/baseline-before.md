## 1. 동시 주문 — 주문번호 충돌 (`OrderNoConcurrencyTest`)

회원 50명이 각자 장바구니 1줄로 동시에 주문 (스레드 16, 시작 신호 `CountDownLatch`).

| 회차 | 실패 | 저장 | DB 의 번호 중복 |
|---|---|---|---|
| 1 | 40 | 10 | 0 |
| 2 | 34 | 16 | 0 |
| 3 | 27 | 23 | 0 |
| 4 | 26 | 24 | 0 |
| 5 | 33 | 17 | 0 |
| **합계** | **160 / 250 (64%)** | 90 | 0 |

- DB 에 중복 번호가 0건인 것은 `orders.order_no` unique 제약이 막았기 때문이다. **제약이 막는 대신 주문 자체가 실패**한다.
- 원인 : `nextOrderNo` 의 `count + exists` 는 커밋 전 다른 트랜잭션의 행을 보지 못한다 (READ COMMITTED). 같은 번호를 받은 주문은 `save()` 즉시 INSERT (IDENTITY) 에서 unique 위반.

## 2. 회원 집계 lost update (`MemberAggregateConcurrencyTest`)

같은 고객이 주문 10건을 넣어 둔 뒤, 기기 20대에서 동시에 "기존 10건 취소 + 새 주문 10건". 실제 요청 경로 (MockMvc, open-in-view 포함).
기대값 = 취소되지 않은 주문에서 다시 계산한 합계.

| 회차 | 새 주문 실패 | 주문 수 (실제 / 기대) | 누적 금액 (실제 / 기대) | 포인트 (실제 / 기대) |
|---|---|---|---|---|
| 1 | 5 | 12 / 5 | 54,000 / 22,500 | 540 / 225 |
| 2 | 6 | 9 / 4 | 40,500 / 18,000 | 405 / 180 |
| 3 | 4 | 11 / 6 | 49,500 / 27,000 | 495 / 270 |
| 4 | 2 | 9 / 8 | 40,500 / 36,000 | 405 / 360 |
| 5 | 3 | 8 / 7 | 36,000 / 31,500 | 360 / 315 |

- 5회 모두 집계가 실제보다 **크다** = 동시 취소의 차감이 덮어써져 사라졌다 (lost update). 포인트가 실제보다 많이 남는다 → 금전 손실.
- 새 주문 실패 (2~6건) 는 1번과 같은 주문번호 충돌.

## 3. 사용자 관점 롤백 (`OrderControllerRollbackTest`)

| 시나리오 | 상태 | 이동 | 안내 | 장바구니 | 주문 행 |
|---|---|---|---|---|---|
| B. 주문 저장 실패 | 500 | 없음 (오류 화면) | 없음 | 1줄 유지 | 0 → 0 |
| 같은 주문서 재제출 | 302 | `/orders` | "이미 처리한 주문서예요. 주문 내역을 확인해 주세요." | — | 0 → 0 |
| A. 오늘 주문번호와 충돌 | 500 | 없음 | 없음 | 1줄 유지 | 1 → 1 |

- 지금 코드에서 장바구니는 남는다 (예외가 `cart.clear()` 보다 먼저 남). 대신 **주문서 토큰이 먼저 폐기**되어, 다시 내면 주문이 없는데 "이미 처리했다"고 안내한다.

## 4. 서비스 계층 롤백 (`OrderPlaceRollbackTest`)

| 시나리오 | 주문 행 | 주문상품 행 | 장바구니 |
|---|---|---|---|
| 저장 직후 실패 (INSERT 후 예외) | 0 → 0 | 0 → 0 | 1줄 유지 — **통과** |
| `place` 반환 뒤 커밋 직전 실패 | 0 → 0 | — | **1줄 → 0줄** — 실패 |

- DB 롤백은 이미 정상이다. 문제는 **세션 상태(장바구니·토큰)가 트랜잭션 밖에 있다**는 것.
- 커밋 시점 실패 (예 : 낙관적 락 충돌) 가 생기면 장바구니가 사라진다. `@Version` 같은 수정이 오히려 이 경로를 열 수 있어 미리 막아 둔다.

## 수정 코드가 지켜야 할 계약 (테스트가 기대하는 것)

1. `OrderService.place(Member, Cart, PickupType, String)` 시그니처 유지, **장바구니를 비우지 않는다** (비우기는 커밋 성공 뒤 호출한 쪽).
2. 주문 저장은 `OrderRepository.save` 또는 `saveAndFlush` 를 거친다 (테스트의 장애 주입 지점).
3. `POST /order` 실패 시 : **3xx 리다이렉트로 `/order`** (주문서), flash `errorMessage` 에 안내 ("이미 처리한" 문구 금지), 장바구니 유지, 이후 `GET /order` 로 받은 새 토큰으로 다시 주문 가능.
4. 실패 후 **옛 토큰으로 재제출**해도 `/orders` 로 보내거나 "이미 처리한" 이라고 안내하지 않는다.
5. 회원 집계는 동시 주문·취소에서도 취소 안 된 주문의 합계와 같다.
6. 동시 주문 50건이 실패 없이 모두 저장되고 번호가 겹치지 않는다.
